# Build, installation and redistribution evidence

The release workflow checks source SHA, Android application/version identity,
dependency checksums, asset provenance, emulator installation and instrumentation.
This establishes software delivery evidence. Four physical Joy-Con controllers,
AR tracking, audible output and motion-to-sound latency remain `HARDWARE_PENDING`.

## Artifacts and gates

Each debug artifact includes the APK, SHA256SUMS, `JoyDurm-debug.json`, exact APK
asset manifests and a CycloneDX runtime SBOM. The identity JSON binds the full
source commit, APK SHA-256, certificate SHA-256, package name and Android version.
The installation artifact contains the same APK identity plus device model,
serial, OS fingerprint/API/ABI, instrumentation text, JUnit XML and Logcat.
Reports from another commit are not evidence for the new APK.

CI installs the prebuilt APK from the successful build job, and uses the matching
prebuilt test APK. Tests cover denied camera permission with continued ordinary
3D touch input, actual composed-screen model visibility, Activity pause/resume/recreation, legacy neutral migration and
ControllerHub restart/real UDP clock exchange. The XML gate requires every
named test to run and pass; skipped or missing cases fail. Old reports are removed
before execution, and the XML run ID must match the unique ID passed to this
runner invocation. A previous successful XML cannot validate an interrupted run.
An emulator can check
these behaviors but cannot verify sound actually reached the user's ear or that
the phone driver exposes Joy-Con IMU sensors.

CI uses the supported `swangle` software graphics backend. The previous
`swiftshader_indirect` mode is deprecated as of Emulator 36.4.9; see the
[official Android graphics acceleration documentation](https://developer.android.com/studio/run/emulator-acceleration#accel-graphics).
The composed-screen model visibility assertion remains mandatory and retains its
original pixel threshold. A passing test on the local arm64 emulator is not
substituted for this Linux x86_64 CI result.
The installation artifact also retains `ordinary-3d-screen.png` and the matching
run-ID-bearing `ordinary-3d-visibility.json`, including scene bounds, native surface
size, viewport, entity counts and measured pixels, whether visibility passes or
fails. These are the displayed-screen evidence, rather than a Surface-only capture.

`adb install -r` in this job is a **same-version reinstall**. It is not an upgrade
test. CI debug keys are ephemeral between runners; upgrading an earlier APK and
retaining user data remains pending until a previous version and stable signing
identity are supplied. No production key or signing identity is generated here.

Release tags must exactly equal `v<versionName>`, and versionCode must exceed
the reviewed source baseline in `release-baseline.json`. Maintain that baseline
after a verified release. When a configured production keystore is present,
`vars.RELEASE_CERT_SHA256` must contain its explicit expected certificate digest.
Missing or mismatched identity fails signing. Signing remains in a separate job
with no checkout, repository script execution, Gradle or restored build cache.
It only consumes APK/data artifacts from the successful current build and
emulator run. Without release secrets, only the clearly labeled debug pre-release
is eligible. Signed APK upgrade acceptance also remains pending.

All Actions use full official commit identities recorded in `action-pins.json`.
Gradle runs with strict dependency verification. Initial checksum records are a
trust decision about the downloaded bytes, not proof of vulnerability absence
or licensing. The Linux AAPT2 classifier was fetched from Google's official
Maven and checked against its published checksum; provenance is recorded in
`dependency-checksum-provenance.json`.

## Asset inventory and license scope

`assets-manifest.json` separates six app-authored model/license/notice files
from twenty assets inherited from the resolved SceneView/ARSceneView 2.3.0 AARs.
Every dependency asset has an exact path and content digest, Maven coordinate,
AAR digest, fixed upstream source commit and verified license evidence. The
upstream license is saved as `SCENEVIEW-2.3.0-LICENSE.txt`; its fixed source and
hash are in `dependency-asset-license.json`. No wildcard exemption is used for
dependency resources. Any added/replaced model, sound or texture needs a new
reviewed record and redistribution permission before it can pass the APK gate.

The release variant additionally packages two explicitly named build-generated
baseline profile files under `dexopt/`. Their digests vary with the source build,
so the final APK-specific manifest records the actual generated bytes and APK
hash. They are performance metadata compiled by AGP, rather than imported media.

The original procedural GLB is CC0. Built-in drum sounds are synthesized by
original MIT-licensed JoyDurm code at runtime; no external drum sample is bundled.
User imports are local runtime files and are not republished as project assets.
The SBOM enumerates resolved runtime artifacts and hashes, including metadata/BOM
nodes with no packaged artifact. It does not infer redistribution permission
from a missing SPDX license entry. Existing NOTICE and bundled license texts
retain the upstream license distinctions. A full transitive license/vulnerability
review remains a separate release task.

## Reproduce software gates

```sh
python3 -m unittest discover -s tools/verification -v
python3 -m unittest tools/test_glb_hierarchy.py -v
python3 tools/verification/verify_assets.py --apk app/build/outputs/apk/debug/app-debug.apk
./gradlew --no-daemon --dependency-verification=strict testDebugUnitTest lintDebug lintRelease assembleDebug assembleDebugAndroidTest assembleRelease
./gradlew --no-daemon --dependency-verification=strict -I tools/verification/sbom.init.gradle :app:exportRuntimeSbom
python3 tools/verification/verify_sbom.py app/build/reports/sbom/runtime.cdx.json
```

The instrumentation job captures the actual installation/test evidence. CI job
definitions or a successful APK compilation alone must not be reported as a
passed instrumentation run, stable signed release, version upgrade or hardware
acceptance.
