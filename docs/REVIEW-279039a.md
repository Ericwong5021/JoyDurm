## 三、核心问题：输入、姿态、空间命中与脚部交互

以下 `input/`、`core/`、`audio/`、`render/`、`ui/` 均相对于：

```text
app/src/main/java/ai/joydurm/
```

严重度定义：**P0 是产品入口必须先验证的条件；P1 是核心演奏可靠性或交付阻断；P2 是完善项及发行前应关闭的风险。** P0 不表示已证明所有 Android 手机都无法连接。

### F01｜P0，硬件与系统风险：Android 直连尚未形成已验证的支持范围

**证据：**`input/ControllerHub.kt` 的 `attach()`、`openHid()`、`listenBridge()`。当前实际上只有三条路径：

| 路径 | 当前实现 | 尚不能据此保证的事情 |
|---|---|---|
| 系统控制器传感器 | API 31+ 调用 `InputDevice.sensorManager`，要求同时存在加速度计与陀螺仪 | 蓝牙配对、按键可用，不保证驱动开放 IMU，也不保证四路持续采样 |
| 原始 HID | 打开 `/dev/hidrawN`，发送初始化命令并读取报告 | 普通 APK 安装后并不会自动获得设备节点权限 |
| 桌面桥接 | 电脑 HIDAPI 读取 Joy-Con，UDP 发给 Android | 这需要电脑参与，不是纯 Android 无辅助设备直连 |

**修复建议：**先新增 `CapabilityProbe`，导出手机系统版本、设备 descriptor/VID/PID、传感器列表、实际采样率、时间戳和四只物理手柄身份。兼容性文档只填入有数据证据的机型，不用“Android 12+”代替“已验证支持”。

**验收方法：**从一只扩展到四只，逐只静止、六面朝向、三轴转动，证明数据来自对应手柄；四路连续记录至少 10 分钟。权限拒绝、只有按键无 IMU、失联时要明确降级。

还有一个需要更新旧认知的点：**本次查询的 Android 官方文档已经列出 version 37.1 的 `android.hardware.hid.HidManager`，但 `ACCESS_HID` 的保护级别是 `internal|appop`。** 这应单列 SDK、系统授权和设备可用性验证，不能说“Android 永远没有这样的接口”，也不能说“升级 compileSdk、加一个普通权限申请就解决了”。当前仓库并未实现这条路径。:chatgpt-content-reference{index="12"}

### F02｜P1，确定缺陷：UDP 把接收时刻当成采样时刻

**证据：**`ControllerHub.listenBridge()` 使用：

```kotlin
now - (samples.size - 1 - i) * 5_000_000L
```

构造样本时间；Python 发出的 v1 数据没有源采样时间和连接会话标识。`InputHealth.accept()` 又按这个时间进行新鲜度及单调性判断。  

**影响：**除了 R4 的误丢样本，带有效递增序号的延迟载荷也会被重新标成“现在”，无法准确识别陈旧动作。姿态积分、脚手同步和延迟统计因此都可能失真。现有 `delayedBatchCannotMakeOldMotionFresh` 测试直接向健康检查传入旧时间，**没有覆盖 UDP 重新打时间戳这一层**。

**修复建议：**协议 v2 增加 `sessionId`、物理设备 ID、序号、原始报告 timer、桥接端单调读取时间和样本时间估计。实现带误差界的时钟映射、有界重排和陈旧丢弃；分开统计包接受数、样本接受数、丢包、重复、乱序和抖动。不能用 `last + 1` 或重新赋 `now` 掩盖问题。

**验收方法：**相同源记录经过批量到达、50～500 ms 延迟、乱序、复制、丢包、计数器回绕和进程重启后，产生相同有效动作序列，或按明确的过期策略丢弃；不得补播旧击打。需要补真实 UDP 集成测试，而不止公式夹具。

### F03｜P1，确定缺陷：姿态滤波不适合复合旋转

**证据：**`core/Motion.kt → OrientationFilter.update()` 直接执行 `pitch -= gx*dt`、`roll -= gy*dt`、`yaw += gz*dt`。R2 已证明问题不需要硬件噪声也能出现。

**影响：**抬高手臂、交叉敲击、改变握持姿态时，鼓件方向会随错误的姿态估计移动；不能靠增加“重新归中”按钮彻底修好。

**修复建议：**先统一左右 Joy-Con、不同输入路径和佩戴方式的坐标变换，再采用经过验证的四元数融合。可评估固定版本的 MIT 项目 `xioTechnologies/Fusion`，保留静置零偏校准和动态加速度拒绝，并严格处理库接口单位。六轴融合仍不提供绝对位置，也不能凭空消除没有外部参考时的 yaw 漂移。:chatgpt-content-reference{index="18"}

**验收方法：**用已知四元数生成三轴转动、倾斜叠加 yaw、倒置、跨 ±π、不同采样率和丢帧轨迹；随后再用真实数据和外部参考测漂移。不能只测小角度正负号。

### F04｜P1，确定缺陷：重连、暂停和重启后的归中坐标不一致

**证据：**`DrumEngine.deviceLost()` 重置滤波器却保留 `neutral`；`SettingsStore.load()` 还会把旧 `neutral` 恢复到一个全新的滤波器。`MainActivity.onPause()` 会停止输入，触发相关状态清理。  

**影响：**R1 的 −57.30° 偏移会让“同一个物理方向”突然对应另一个鼓区。

**修复建议：**区分持久化物理校准与会话内归中，引入 `OrientationEpoch`。无法保持姿态连续性的重连进入 `NEEDS_RECENTER`，禁止继续按旧空间标定击打；不能简单把 `neutral` 改成零就称为恢复原方向。

**验收方法：**对非零 yaw 归中后分别测试断连、后台恢复、进程重启和长采样间隙。恢复后要么方向一致，要么明确待归中且无误击。

### F05｜P1，确定架构缺口：画面里的鼓组位置不参与命中

**证据：**`Target` 只有 `drum/yaw/pitch`；`DrumEngine.process()` 按姿态距离选鼓。`DrumScene.setPiecePosition()` 修改的是视觉节点，引擎不读取鼓件 XYZ、半径、平面或 AR 锚点。  

**影响：**当前实现是：

> 挥击检测 → 姿态分区选鼓 → 发声 → 对应鼓件动画。

不是：

> 鼓棒尖端穿过眼前 3D 鼓面 → 空间碰撞命中。

**修复建议：**建立共享 `DrumLayout`，包含鼓 ID、位姿、尺寸、触发区域和 `layoutRevision`，由判定与渲染共同使用。第一阶段可交付明确的姿态分区模式，但布局变化必须重映射或使旧标定失效。需要几何近似时，可采用标定后的虚拟手腕支点、棒长与四元数，进行扫掠线段／鼓面相交；自由移动的真正六自由度命中则需要额外位置观测。ARCore 场景锚点本身不是 Joy-Con 位置传感器。:chatgpt-content-reference{index="25"}

**验收方法：**交换两个鼓、整体旋转 90°、改比例和重新摆放锚点，画面与命中必须一致，或明确要求重标定。几何模式还要测试前伸、后缩和肘部平移，不能只测原地转腕。

### F06｜P1，算法风险：减速时触发，再用当时姿态选鼓

**证据：**`StrokeDetector.update()` 在速度跌到峰值 72% 以下时触发，`DrumEngine.process()` 随后使用当前姿态选择目标；默认 90 ms 冷却，目标距离阈值又相对宽。 

**影响：**可能晚响、在峰值后跨入邻区而串鼓，快速同手连击也可能受冷却限制。**这些规则确定存在，但真实误击率和手感尚未测量。**

**修复建议：**记录挥击开始、峰值、减速和候选命中时刻的姿态；引入目标置信度与模糊区拒绝，用标注回放比较不同触发策略。不要靠把冷却降为零解决快打。

**验收方法：**输出单击、回弹、横扫、交叉手、轮鼓、同手连续和左右交替的混淆矩阵、漏击与双发统计。

### F07｜P1，确定缺陷：右脚不能区分卸载与踩击，方向设置无效

**证据：**`DrumEngine.process() → RIGHT_FOOT` 使用：

```kotlin
abs(sample.accel.norm() - 9.80665)
```

其路径不读取 `state.axis/sign`；UI 却提供这些方向设置。 

**影响：**低重力卸载和正向冲击都被变成正值，R3 已复现多一次 kick。现有“静止不触发”测试不等于“抬脚不触发”。

**修复建议：**单独实现 `KickDetector`，依据佩戴坐标系中的去重力加速度投影、角速度和 `REST → LIFT → DOWN → FIRED → RECOVERY` 顺序判定；有效接入参数，删除无效控件。

**验收方法：**仅抬起、慢放、停在半空、轻晃、强弱下踩和左右脚同时动作分别测试。建议以“200 次纯抬脚零 kick、200 次明确踩击无双发”作为后续验收门槛，而不是当前成绩。

### F08｜P1，确定能力缺口＋佩戴风险：左脚只使用 pitch

**证据：**左脚路径只有相对 pitch、`hatSign` 和角度范围；开度平滑为固定 `0.35/sample`，通用 axis 和击打阈值不影响它。

**影响：**换一种安装朝向后，脚尖抬升可能主要反映在 roll；采样率变化会改变平滑手感。当前 UI 不能充分表达这种限制。

**修复建议：**实现平放／全开两点标定、脚部铰链轴与佩戴变换，改为按 `dt` 平滑，增加开闭滞回；连续开度、CHICK 和失联止音分别建模。

**验收方法：**不同 Joy-Con 左右型号、安装方向及采样率下，都满足平放闭合、抬起连续开镲、慢闭／快闭行为明确，并验证半开保持和与手击同刻闭镲。

## 五、建议采用的架构，不做无关重写

建议保留 **Kotlin＋AndroidX＋SceneView／ARCore＋HIDAPI 桥接** 的主体，把数据合同和线程边界重新理清：

```text
输入适配器
  系统控制器传感器 / 实验性 raw HID / 桌面 UDP v2
        ↓
身份、会话、单位、轴向、采样时钟统一
        ↓
有界样本与命令队列
        ↓
单写者 EngineExecutor
  ├─ 物理设备校准
  ├─ 四元数姿态 + OrientationEpoch
  ├─ 左右手 StrokeDetector
  ├─ 独立 KickDetector
  ├─ HiHatController
  └─ 共享 DrumLayout 的 HitMapper
        ├─ HitEvent / HatControl / ChokeAll → AudioSink
        └─ 不可变 EngineSnapshot → 3D / AR 渲染
```

需要先统一的合同是：

| 合同 | 必须解决的问题 |
|---|---|
| `ControllerIdentity / SessionId` | 物理手柄身份不等于 HID path；重连不能混用旧序列 |
| `ImuFrame` | 区分采样时间估计、主机读取时间、手机接收时间和时钟误差 |
| `OrientationEpoch` | 归中角只对相应姿态坐标原点有效 |
| `DrumLayout / layoutRevision` | 视觉布局和命中使用同一版本 |
| `HitEvent / HatControl` | 击打、连续开度、CHICK 和失联止音不是同一种事件 |
| `EngineSnapshot` | UI 与渲染不直接读取多线程修改中的 RoleState |

**执行顺序上，先稳定这些合同，再并行处理传输、姿态四肢、音频和 AR。** 否则多个 Agent 很容易各自定义一套时间、坐标和状态，最后集中在 `MainActivity`、`DrumEngine` 上发生集成冲突。

空间能力也应分层：先完成诚实、稳定的姿态分区模式和布局一致性，再验证受约束虚拟棒；没有外部位置观测，不应承诺自由六自由度空间碰撞。

## 七、最终交付不能缺少的验收证据

**软件修复完成**与**产品硬件验收完成**应分别记录。

软件交付至少包含最终 commit、F01～F21 关闭表、自动测试报告、安装过的 APK 与 SHA256、版本与证书信息、回放工具、用户操作说明、许可清单和真实已知问题。

四手柄＋AR 验收还必须包含：

| 维度 | 最低验证内容 |
|---|---|
| 四路输入 | 四只物理设备身份明确，逐只断开不会替换其他角色；原始样本和实际采样率可查看 |
| 双手 | 单击、回弹、横扫、交叉、同手连续、交替快打；记录漏击、双发和串鼓 |
| 左脚 | 平放、逐步抬升、半开保持、全开、慢闭与快闭；闭镲与手击同时发生的顺序明确 |
| 右脚 | 仅抬起不响、一次踩下只响一次；与左脚独立工作 |
| 延迟 | 直连／桥接、1／4 手柄、AR 开／关、扬声器／有线分别测量，不混成一个平均数 |
| 生命周期 | 后台恢复、进程重启、桥接关闭／重启、网络抖动、单设备失联和重新归中 |
| AR | 真机锚定、移动手机、失跟踪、重新摆放、不支持设备降级 |
| 持续运行 | 至少 30 分钟四手柄＋AR 联合演奏，建议补 60 分钟热稳定测试 |

可将单目标 precision ≥98%、recall ≥95%，以及前述脚部 200 次测试作为后续工程门槛；**这些都是建议验收值，不是当前项目成绩。** 延迟指标也应在测量方法和误差界确定后制定，不能拿音频缓冲区长度代替“动作到实际出声”。
