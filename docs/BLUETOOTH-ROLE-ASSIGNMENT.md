# Bluetooth role assignment (0.3.2)

Clicking any of the four role assignment controls opens a single native Bluetooth device picker. It reads actual paired devices and offers classic discovery, preserving original names (including L/R and −/+) and MAC addresses. Android 12+ requests CONNECT and SCAN as runtime nearby-device permissions. Android 8–11 uses the legacy Bluetooth permissions and requests location only for discovery. Scan results are not used to derive location.

Selecting a device associates its physical address with the role immediately and calls the public `BluetoothDevice.createBond()` when unpaired. Android owns pairing confirmation; bond broadcasts update the same window. Role selection, pairing, and fresh IMU readiness are separate states. A paired device is never declared motion-ready without accepted samples. Denial, disabled Bluetooth, no devices, discovery failure, immediate bond failure, cancelled/failed bond results and retries remain visible in the picker. Repeated assignment commands retain one window. Moving a physical device to another role requires explicit confirmation. Choices survive recreation/restart.

Android 35's public InputDevice API provides a descriptor and sensor manager, but no Bluetooth MAC address; it cannot reliably map two identically named Joy-Cons to their selected addresses. The app therefore offers explicit association with a real ControllerHub input, showing that input's actual ID, transport, and fresh-IMU state. It does not guess from device names. HID host connection is managed by the system: the picker links to system Bluetooth for connection when needed. No hidden APIs, root, invented devices, arbitrary RFCOMM UUID or fake IMU stream are introduced. No IMU means calibration and motion playing remain unavailable; touch pads still work.

A regression exposed an independent UDP health bug: the input watchdog captured its tick before `decoder.poll()` delivered samples, then expired their health against that earlier tick. Receipt timestamps later than the tick were interpreted as a negative age, clearing motion immediately. Expiry now reads the monotonic clock after delivery. The existing 3s health, 100ms action freshness and clock error bounds remain unchanged.

Validation adds six JVM tests and four Android cases to the previous 119/11. Android radio-result fixtures cover state transitions only and explicitly retain HARDWARE_PENDING; a separate real UDP socket/clock test checks explicit input association, fresh motion and loss. The original eleven display/navigation/UDP cases remain required. User phone Bluetooth/IMU capability and physical Joy-Con pairing still need hardware evidence.
